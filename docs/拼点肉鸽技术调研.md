# 拼点战斗 × 卡牌肉鸽：GitHub 技术调研

调研日期：2026-10-26。范围：公开 GitHub 仓库及关键源文件。已阅读代码，未克隆、安装、运行或进行性能测试。本文是研究与工程建议，不是已经确认的游戏需求。按用户最新要求先调研，不进行需求访谈。

## 结论

可以实现。建议把项目拆成三个相对独立的部分：拼点规则、战斗演出、肉鸽流程。现有仓库可以帮助搭建牌组、路线、奖励等通用系统，但本次没有找到经过验证、可以直接组合成“边狱巴士拼点 + 杀戮尖塔肉鸽”的成品模板。

针对当前的二维战斗设想，优先考虑 Godot 4。先做一场原创素材的拼点战斗，再接一小段肉鸽流程，比立即接入大型框架更容易判断核心体验。引擎建议是本次工程判断，尚未成为用户决定。

## 拼点规则应如何实现

以下是建议的简化原创规则，不是对原作完整规则的复刻说明。

1. 玩家选择技能与目标，敌人提前公布计划行动。
2. 系统将互相对抗的技能配成一组，其他行动按约定单独结算。
3. 每轮根据双方当前硬币与状态计算威力，比较结果。
4. 失败方移除一枚可破坏硬币，平局重新判定；直到一方无币，或触发约定的平局上限。
5. 胜方按剩余硬币执行攻击并结算伤害、状态与死亡。

简单例子：基础威力 4、两枚每枚 +3 的硬币，可能得到 4、7、10。若第一轮输掉一币，之后范围变为 4 或 7。最大值相同的技能，硬币数不同，最终胜率与输出也可能不同。

需要明确区分“计算胜率”和“实际抽样”：预览可以枚举概率或模拟，真正战斗只抽取本次结果。预览与画面特效不得消耗战斗随机数，否则多看一次提示、改变帧率都可能影响胜负。

先不加入所有特殊硬币、速度抢夺、群攻、复杂精神值与大量状态。这些内容会扩大配对与结算顺序的组合数量，适合后续逐项扩展。

## 拼点画面怎么做

不是只有角色位移。建议用同一条演出时间线协调：

| 阶段 | 画面与声音 | 对应逻辑事件 |
| --- | --- | --- |
| 对峙 | 强调技能、目标和威力范围 | 行动配对完成 |
| 接近 | 双方前冲，镜头收拢 | 开始一轮拼点 |
| 判定 | 翻币、数字跳动与确认音 | 本轮结果已生成 |
| 撞击 | 闪光、火花、轻微震屏、短暂停顿 | 碰撞时刻 |
| 破币 | 失败方后退、硬币破裂 | 硬币减少 |
| 再次对撞或追击 | 继续判定，或胜者连击 | 拼点继续或结束 |
| 收尾 | 伤害、血条、状态与镜头归位 | 行动完成 |

原型先用少量待机、出手、受击姿势，配合位移、残影、刀光和音效。骨骼动画与高质量逐帧动画可以后续替换。先保证撞击时刻、声音和数值确认对齐，再增加粒子数量。

实现建议：规则层产出事件记录，表现层消费记录。Godot 可用 AnimationPlayer/Tween 组织动作，Camera2D 管理镜头，粒子与着色效果负责火花和闪白。这些是拟采用的工程方案，并非对原游戏内部实现的断言。

暂停、倍速和跳过动画都只改变呈现速度，不重复结算伤害。跳过时把显示状态同步到已算出的最终结果。打击停顿优先暂停角色与特效时间，不随意冻结整棵场景树造成 UI 或等待信号卡死。

## 与肉鸽流程的衔接

整局循环建议为：选择路线 → 战斗或事件 → 领取奖励 → 调整牌组/技能 → 下一节点 → Boss → 本局结算。

一个可验证的混合方案是：保留抽牌与能量，但每轮先让玩家将攻击牌分配给敌方行动槽，确认后统一拼点；增益、防御和没有对抗目标的攻击按单独约定结算。这会明显改变传统“出一张牌立即生效”的节奏，所以仅作为原型候选。

另一个方案是保留传统出牌，只在攻击指向可拼点的敌人行动时触发对抗。改动可能较小，但必须解决敌人行动是否被消耗、是否能反复挑战同一行动、剩余行动何时执行等问题。

在用户继续提出想法之前，两种方案都保留，不将任何一种写死成需求。

## 建议的工程边界

- Content：角色、技能、卡牌、敌人、遗物等静态定义；使用稳定 ID，文本和显示名不作存档键。
- BattleState：生命、硬币、状态、手牌、行动槽等运行时数据。
- Resolver：配对、拼点、伤害、状态触发、死亡与胜负；不依赖画面节点才能运行。
- BattleEvents：可按顺序播放的判定与状态变化记录。
- Presenter：角色、镜头、音效、数字、UI；不独立再算一遍伤害。
- RunState：路线、奖励、牌组、金币与随机数状态；战斗结束后接收结果。

初期不需要做通用插件平台，也不需要先实现完整内容编辑器。用少量数据定义配合清晰的结算函数即可。

## 最容易低估的工作

1. 规则顺序：受击、破币、状态触发、反击与死亡的先后，会改变结果。需要单一结算入口。
2. 双重随机：抽不到合适牌再拼点失败，容易让玩家感觉无法决策。奖励与技能应提供控制风险的手段，而非只增加随机。
3. 演出时长：多角色、多硬币会放大战斗等待。需要可加速、重复碰撞精简以及关键信息仍可读。
4. 内容平衡：新增一个状态或遗物可能影响很多技能；后期工作量更多来自内容交互，而不是地图页面。
5. 模板迁移：教程工程的低分辨率和交替回合假设，不能照搬到高清多角色拼点玩法。

## 建议实施顺序与验收

| 阶段 | 最小范围 | 通过条件 |
| --- | --- | --- |
| 1. 纯规则 | 两个单位、三种技能、正面概率、破币、平局上限 | 同种子同结果；零币、平局、死亡边界正确；预览不影响结果 |
| 2. 单场演出 | 对撞、破币、追击、受击、音效、倍速 | 画面与规则记录一致；跳过和倍速不改变最终状态 |
| 3. 短肉鸽 | 约五个可经过的节点、奖励、一个事件、一次升级、一个 Boss | 可从开局走到胜败结算；可以开始新一局 |
| 4. 扩展验证 | 少量遗物、状态与更多敌人 | 至少出现两种有效玩法；奖励确实影响下一战的选择 |

这不是工期承诺。先完成第一、二阶段，才能判断用户期望的画面质量、角色数量与内容规模对应的实际成本。
